LLM 애플리케이션을 만들다 보면 LangChain과 LangGraph 중 무엇을 사용해야 할지 고민하게 된다. “LangChain은 순차 처리, LangGraph는 분기 처리” 또는 “LangGraph에만 상태가 있다”라고 설명하면 이해하기 쉽지만, 실제 기능을 정확하게 구분하지는 못한다.

두 도구의 핵심 차이는 **추상화 수준과 개발자가 실행 흐름을 직접 제어하는 범위**다. LangChain은 모델과 도구를 연결해 에이전트를 빠르게 구성할 수 있게 하고, LangGraph는 상태를 유지하는 실행 흐름을 세밀하게 설계할 수 있게 한다. 이 글은 2026년 11월 공식 문서와 개념을 기준으로 한다.

## **1. LangChain이란?**
{: .mt-5 .mb-2}

LangChain은 LLM을 사용하는 애플리케이션을 만들기 위한 프레임워크다. 모델과 프롬프트, 검색, 도구 등을 연결하고 에이전트를 구성할 때 사용한다. 예를 들어 사내 문서를 검색해 질문에 답하는 기능을 다음과 같이 구성할 수 있다.

```text
문서 준비: PDF → 텍스트 분할 → 임베딩 → 검색용 저장소에 저장
질문 처리: 사용자 질문 → 관련 문서 검색 → LLM 답변 생성
```

문서 준비는 미리 수행할 수 있고, 질문 처리 시 매번 PDF를 다시 임베딩할 필요는 없다. LangChain의 모델·검색 관련 구성 요소를 연결해 이런 기능을 만들 수 있다. 단순한 모델 호출이나 일반 코드로도 구현할 수 있으므로 LangChain이 필수인 것은 아니다.

## **2. LangGraph란?**
{: .mt-5 .mb-2}

LangGraph는 상태를 유지하는 에이전트와 워크플로의 실행을 구성하는 프레임워크다. 여러 작업을 **노드(node)**로 나누고, 작업 사이의 이동을 **엣지(edge)**로 정의하며, 각 단계가 사용할 정보를 **상태(state)**로 관리할 수 있다.

```text
질문 → 문서 검색 → 검색 결과 판단
                        ├─ 충분함 → 답변 생성 → 완료
                        └─ 부족함 → 검색어 수정 → 문서 검색
```

예를 들어 상태에 질문, 검색 결과, 검색 횟수, 판단 결과를 담을 수 있다. 재검색 횟수가 한도에 도달하면 담당자에게 넘기도록 흐름을 설계할 수도 있다. 실행을 저장하고 나중에 재개하려면 적절한 체크포인터 등 지속성 설정이 필요하다. [LangGraph 워크플로 설계 가이드](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph)

## **3. 두 도구는 어떤 관계일까?**
{: .mt-5 .mb-2}

LangChain과 LangGraph는 별개의 라이브러리이며, 함께 사용할 수 있다. LangChain의 에이전트 구현은 내부적으로 LangGraph의 구성 요소를 사용한다. 개발자는 LangChain의 에이전트를 사용해 빠르게 시작할 수도 있고, 더 세밀한 제어가 필요할 때 LangGraph를 직접 사용할 수도 있다. [공식 학습 문서](https://docs.langchain.com/oss/python/learn)

```text
LangChain 에이전트 ── 내부 실행에 LangGraph 활용

LangGraph로 직접 구성한 흐름
├─ 검색 단계 ── LangChain의 검색 구성 요소 사용 가능
├─ 판단 단계 ── LangChain을 통해 LLM 호출 가능
└─ 분기·반복·승인 대기 ── 개발자가 흐름 설계
```

LangGraph를 사용할 때 모든 노드를 LangChain으로 만들어야 하는 것은 아니다. 일반 Python 함수, 직접 호출한 모델 API, 기존 서비스도 노드에서 사용할 수 있다.

## **4. 자주 헷갈리는 구분**
{: .mt-5 .mb-2}

| 질문 | 설명 |
| --- | --- |
| LangChain은 순차, LangGraph는 분기 처리만 할까? | 아니다. LangChain 에이전트도 상황에 따라 도구를 선택하고 반복 호출할 수 있다. |
| 중간에 판단 과정이 있으면 LangGraph일까? | 아니다. LangChain 에이전트에서도 LLM이 도구 사용 여부 등을 판단할 수 있다. |
| LangGraph에만 상태가 있을까? | 아니다. LangChain 에이전트도 대화 이력 등의 상태를 활용할 수 있다. |
| 그럼 무엇이 다를까? | LangChain은 제공되는 구성 요소와 에이전트를 활용하기 쉽고, LangGraph는 상태와 흐름을 더 직접 정의하고 제어하기 쉽다. |

예를 들어 두 도구 모두 대화 이력을 활용할 수 있다. 반면 검색 횟수, 검토 결과, 담당자 승인 상태를 관리하면서 조건에 따라 재검색하거나 승인을 기다렸다 재개하는 절차를 직접 구성하고 싶다면 LangGraph를 고려할 수 있다. LangChain의 에이전트 기능으로 요구사항이 충분하다면 반드시 LangGraph를 직접 작성할 필요는 없다.

## **5. 검색 결과가 부족한지는 누가 판단할까?**
{: .mt-5 .mb-2}

LangGraph가 결과를 보고 자동으로 부족하다고 판단하는 것은 아니다. **개발자가 판단 기준과 다음 경로를 설계**하고, 프로그램의 규칙이나 LLM이 실제 판단을 수행한다.

| 방식 | 판단 예시 | 고려할 점 |
| --- | --- | --- |
| 규칙 기반 | 검색 결과가 3개 미만이거나 점수가 기준보다 낮으면 재검색 | 빠르고 예측하기 쉽지만 결과의 실제 관련성을 완전히 보장하지 못한다. |
| LLM 기반 | 검색된 문서로 질문에 답할 수 있는지 LLM에 평가 요청 | 문맥을 고려할 수 있지만 판단이 틀리거나 일관되지 않을 수 있다. |

두 방식을 조합할 수도 있다. 어떤 방식을 사용하든 재검색 횟수의 상한과, 한도에 도달했을 때의 처리 방법을 정해야 무한 반복을 피할 수 있다.

## **6. 예시: 고객지원 챗봇**
{: .mt-5 .mb-2}

### **LangChain으로 구성하는 문서 검색과 답변**
{: .mt-4 .mb-2}

사용자가 제품 사용법을 물으면 관련 문서를 검색하고, 검색된 내용을 기반으로 답변과 출처를 제공한다.

| 기능 | 처리 내용 |
| --- | --- |
| 문서 검색 | 질문과 관련된 사내 문서를 가져온다. |
| 답변 생성 | 질문과 검색된 문서를 모델에 전달해 답변을 작성한다. |
| 출처 표시 | 답변에 사용한 문서의 제목이나 링크를 제공한다. |
| 정보 부족 | 근거가 부족하면 모른다고 알리고 담당자 문의를 안내한다. |

이 기능에서는 LangChain으로 모델과 검색 구성 요소를 연결할 수 있다. 단순한 검색과 답변만 필요하다면 LangGraph를 직접 구성하지 않아도 된다.

### **LangGraph로 구성하는 검토와 재검색**
{: .mt-4 .mb-2}

요구사항이 “검색 결과가 부족하면 다시 검색하고, 중요한 요청은 담당자 승인을 받는다”로 확장되었다고 가정하자.

```text
문의 분류
├─ 일반 문의 → 검색 → 결과 판단
│                     ├─ 충분함 → 답변 작성
│                     └─ 부족함 → 검색어 수정 → 재검색
└─ 환불 요청 → 담당자 승인 대기
                    ├─ 승인 → 환불 시스템에 요청
                    └─ 거절 → 사용자에게 안내
```

| 단계 | 상태에 기록할 수 있는 정보 | 다음 동작 |
| --- | --- | --- |
| 문의 분류 | 문의 유형 | 일반 문의와 환불 요청을 구분한다. |
| 검색 및 판단 | 검색 결과, 충분 여부, 검색 횟수 | 충분하면 답변하고, 부족하면 한도 내에서 재검색한다. |
| 승인 대기 | 요청 내용, 승인 상태 | 담당자 응답을 기다린 뒤 승인 여부에 따라 진행한다. |
| 요청 처리 | 처리 결과, 오류 정보 | 결과를 기록하고 사용자에게 안내한다. |

승인 대기와 재개를 사용하려면 상태를 보존할 체크포인터를 구성해야 한다. 실제 환불 API 연결과 승인 권한 검증도 애플리케이션에서 별도로 구현해야 한다.

## **7. 예시: 채용 지원서 검토**
{: .mt-5 .mb-2}

지원서와 채용 공고를 읽어 **관련 경험과 추가 확인 사항을 요약**하는 단계는 LangChain의 문서 처리와 모델 연결을 활용해 구성할 수 있다. 요약에는 지원서의 근거 문장을 함께 표시하고, 없는 정보는 추측하지 않도록 설계한다.

여기에 “필수 제출 자료가 빠지면 보완 요청을 준비하고, 재제출 후 확인을 이어간다”는 요구가 추가되면 LangGraph로 다음 흐름을 설계할 수 있다.

```text
지원서 접수 → 필수 자료 확인
                ├─ 모두 제출됨 → 요약 → 담당자 검토
                └─ 자료 누락 → 담당자 검토 → 보완 요청
                                                  ↓
                                      재제출 대기 → 자료 재확인
```

상태에는 제출된 자료, 누락 자료, 보완 요청 횟수, 현재 단계 등을 담을 수 있다. 요약은 담당자의 검토를 돕는 자료로 제공하고, 원문 확인과 채용 판단은 담당자가 수행하도록 설계할 수 있다.

## **8. 언제 무엇을 선택할까?**
{: .mt-5 .mb-2}

| 요구사항 | 시작점 |
| --- | --- |
| 질문 한 번을 보내고 답변받기 | 모델 API를 직접 사용하는 것으로 충분할 수 있다. |
| 모델·검색·도구를 연결한 일반적인 에이전트 | LangChain의 구성 요소와 에이전트를 살펴본다. |
| 조건별 경로와 상태 변경을 직접 정의 | LangGraph를 검토한다. |
| 승인 대기, 중단 후 재개, 복잡한 반복 | LangGraph와 적절한 지속성 설정을 검토한다. |
| 복잡한 흐름 안에서 모델과 검색 도구 사용 | LangGraph와 LangChain을 함께 사용할 수 있다. |

이 표는 기능을 독점적으로 나눈 기준이 아니다. 일반 코드나 다른 프레임워크로도 구현할 수 있으며, LangChain의 에이전트 기능만으로 필요한 흐름을 제공하는지도 먼저 확인하면 된다.
